# goserver

Toy multi-tenant backend wiring together [rr](https://github.com/sirkostya009/rr)
(codegen router), [ggen](https://github.com/sirkostya009/ggen) (codegen JSON) and
[barm](https://github.com/sirkostya009/barm) (query builder) over postgres.

## Layout

What another service imports is at the top level: the types the wire speaks in,
and a client for the api. Everything else sits under `internal/`, where the
compiler keeps it.

```
domain/       the wire and row types (barm + json + pipe
              tags, //ggen:generate), the CreateX inputs barm inserts to get an
              X back, ids, tenant id and context, error sentinels
client/go/    the Go api client: routes generated by cmd/clientgen, types domain's
client/ts/    the TypeScript client and its types, generated by cmd/clientgen
cmd/server/   config -> db -> repository.New -> service.New -> httpapi.New
cmd/migrate/  applies migrations, the only thing that ever does
cmd/clientgen/ writes both clients from the rr routes and the ggen types
internal/
  httpapi/      the rr server: controllers, error handlers, auth and
                tenant guards, logging/recover wrapper, generated router
  service/      business rules, one interface + private impl per file
    container.go  Container, the service layer wired over the repositories
  repository/   barm queries, one interface + private impl per file
    container.go  Container, the data layer wired in one place
    tx.go         transactions, and the handle a call runs on
  migrations/   versioned sql per schema category, plus the runner
    shared/       the shared schema
    tenant/       every tenant schema
  config/       env config (ADDR, DATABASE_URL, LOG_FORMAT, ADMIN_TOKEN)
  auth/         password hashes and the tokens sessions and api keys hand out
  logger/       the dev slog handler: one short line per record
  telemetry/    otel traces, metrics and logs, sentry issues
  errs/         errors that carry the stack they were made on
  pgtest/       postgres for the tests
```

## Tenancy

One postgres database. The `shared` schema holds what tenants have in common,
for now the tenant registry. Every tenant has a schema of its own with its own
tables.

The tenant is whatever the caller's credential belongs to: its token carries
the tenant's id, see Auth. `httpapi.Server` reads it once per request and puts a
`domain.TenantContext` in the request context: the id plus the schema name,
derived from the id by `domain.TenantSchema`. Nothing is looked up: the name is
`tenant_` plus the 16 bytes in lowercase base32hex, 26 characters that never
need quoting and that sort like the id, so by creation time for v7.

Below the api nothing takes a tenant argument. Services pass the context
along, and tenant repositories hand `tenantSchema(ctx)` to barm's
`Schema`, so a call is one round trip: no registry check, no transaction, no
`search_path`. A `//rr:pre` guard on the tenant-scoped controllers answers 401
to a request with no working credential, and 400 to the operator's missing or
malformed `X-Tenant-ID`, so past it the context always carries a tenant, and `MustTenant` panicking means a wiring bug. A tenant that
does not exist shows up as a missing relation and answers 404.

The `Tenant` model names its own schema in its tag (`table:shared.tenants`). A
tenant also has a unique `slug`, which is what `cmd/migrate` takes.

`/api/health` and `/api/auth/login` take no credential, `/api/tenants` takes
the operator's.

## Transactions

A transaction rides the context. `Txer.Begin(&ctx, nil)` opens one and points
ctx at it, so every repository call made with that ctx runs inside it, and a
repository never has to be told which handle to use:

```go
tx, err := s.begin(&ctx)
if err != nil {
        return err
}
defer tx.Rollback()      // undoes nothing once committed
...
return tx.Commit()
```

`ctx` is replaced rather than returned so a caller cannot keep the outer
context by accident and write outside the transaction it just opened. Beginning
one inside another nests it as a savepoint: rolling that back keeps the work
around it. Without a transaction in the context a repository runs on the pool.

`PostService.Create` uses one: it reads the author and writes the post
together, so the post cannot land against an author deleted in between.

## Ids

Every primary key is a postgres `uuid` column with `default uuidv7()`, so ids
are generated by the database and come back through `RETURNING`.

In Go an id is a `domain.ID`, a named type over the standard library's
`uuid.UUID`. On the wire, in JSON, in paths and in `X-Tenant-ID`, every id is
unpadded base64url: 22 characters instead of the 36 of the RFC form. Decoding
is strict, so an id has exactly one spelling, and the RFC form is rejected.
`Scan` and `Value` keep the column a native `uuid`. `domain.TenantID` is the
same thing under its own type, so it cannot be passed where a row id is
expected.

## Migrations

The backend never changes a schema. It reads the version a schema is at and
refuses to start on an outdated shared schema. A registered tenant answers 404
until its schema has been migrated, with no restart needed afterwards.

```sh
go run ./cmd/migrate shared           # the shared schema
go run ./cmd/migrate tenants          # every registered tenant
go run ./cmd/migrate tenant acme      # named tenants, by slug, checked against the registry
go run ./cmd/migrate all              # shared, then tenants
go run ./cmd/migrate status           # versions only
```

A migration is `NNNN_name.sql` under `migrations/shared` or `migrations/tenant`,
numbered without gaps, and names no schema: the runner points `search_path` at
the target. Each one runs in its own transaction under an advisory lock and is
recorded in that schema's `schema_migrations` table. Registering a tenant
through the api does not create its schema, run `migrate tenants` after it.

## Run

```sh
createdb goserver
go run ./cmd/migrate shared
export ADMIN_TOKEN=$(openssl rand -base64 32)
go run ./cmd/server &

ADMIN="Authorization: Bearer $ADMIN_TOKEN"
curl -XPOST localhost:8080/api/tenants -H "$ADMIN" -d '{"slug":"acme","name":"Acme"}'   # note the id
go run ./cmd/migrate tenants
# the first user comes from the operator, who names the tenant
curl -XPOST localhost:8080/api/users -H "$ADMIN" -H "X-Tenant-ID: $ID" \
  -d '{"name":"Guy","email":"guy@acme.io","password":"correct horse battery"}'

curl -c jar -XPOST localhost:8080/api/auth/login -d '{"tenant":"acme","email":"guy@acme.io","password":"correct horse battery"}'
curl -b jar localhost:8080/api/users
curl -b jar -XPOST localhost:8080/api/keys -d '{"name":"ci"}'   # note the token, shown once
curl localhost:8080/api/users -H "Authorization: Bearer $TOKEN"
```

`DATABASE_URL` defaults to `postgres://postgres@localhost:5432/goserver?sslmode=disable`.
It needs postgres 18 for `uuidv7()`.

The image is distroless, no shell, with both binaries. The server is the entrypoint:

```sh
docker build -t goserver .
docker run --rm -e DATABASE_URL=... --entrypoint /migrate goserver all
docker run -p 8080:8080 -e DATABASE_URL=... -e ADMIN_TOKEN=... goserver
```

## Auth

A person logs in with the tenant's slug, their email and password, and gets a
session: an `HttpOnly`, `Secure`, `SameSite=Lax` cookie named
`__Host-session`, good for 30 days. A program uses an api key, sent as
`Authorization: Bearer gsk_...`, which acts as the user who made it. Keys are
made and revoked from a session only, so a leaked key cannot mint another.
`/api/auth/me` says who a credential is.

A token is `gss_` (session) or `gsk_` (key) and the base64url of the tenant's id
and 32 random bytes. The tenant is readable from the token, so finding its
schema costs no lookup, and it is under the hash, so a secret moved to another
tenant opens nothing. The database keeps only the sha-256 of each token and the
argon2id hash of each password. A wrong tenant, email or password fail alike
and take as long.

Writes from another site are refused before anything reads the cookie they
carry (`http.CrossOriginProtection`). Clients that are not browsers send no
`Origin` or `Sec-Fetch-Site` and pass.

`ADMIN_TOKEN` (32+ characters) is the operator: the only credential that reaches
`/api/tenants`, and the only one that sends `X-Tenant-ID`, to act in a tenant,
e.g. to create its first user. Unset, nobody is the operator.

## Logs

`LOG_FORMAT=dev`, the default, writes one short line per record:

```
23:55:58.123 I GET /api/users/{id} [200] 1.86ms
23:55:58.124 E handler err="relation does not exist"
```

No date, one letter per level, quotes only where a value needs them, rounded
durations, groups flattened to dotted keys. The request line goes through
`logger.Request(r, status, dur)`, which names the route the request matched
rather than the path it came in on, so every call of one route reads the same.
Its `status` and `dur` print without their names. It is for reading, not parsing: `LOG_FORMAT=json` switches to the
standard library's json handler, which keeps every field. Both write to stdout.

## Telemetry

Traces, metrics and logs go out over OpenTelemetry, so any OTLP backend takes
them (Grafana, Better Stack, a collector). Sentry gets issues only: panics and
every error logged at Error, wherever in the stack, each carrying the otel trace
and span id, the tenant, and the stack of where the error was made
(`internal/errs`).

Both read their standard env vars. Nothing is on by default:

```sh
OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp.example.com   # all three signals
OTEL_EXPORTER_OTLP_HEADERS=authorization=Bearer%20...
OTEL_TRACES_EXPORTER=console                           # or just one, to stdout
SENTRY_DSN=https://...@sentry.io/1
SENTRY_ENVIRONMENT=production
```

A request is a server span named after its route, each query a child span with
its parameterised text. Arguments are never recorded.

## Test

```sh
go test ./...
```

Api tests are wire tests: stub services, exact response bytes, headers and
status codes for every route, and what each handler bound and passed down.

Everything below the api runs against a real postgres on the server at
`TEST_DATABASE_URL` (default `postgres://postgres@localhost:5432/postgres`),
and skips when none answers. Service tests share one database created for the
test binary and dropped after it: each test gets a pgx transaction on it,
handed to barm as a pool whose transactions are savepoints and rolled back when
the test ends, so
tests stay isolated without a database each. A test that expects the database
to reject something has to end there, since postgres refuses the rest of a
transaction after a failed statement. Repository and migration tests still take
a database each, because they migrate it.

The hooks under `.githooks` run gofmt, vet and golangci-lint before a commit,
and the tests and a stale-codegen check before a push:

```sh
git config core.hooksPath .githooks
```

CI (`.github/workflows/ci.yml`) runs the same, plus the TypeScript client and
the docker build.

## Regenerate

```sh
go generate ./...
```

ggen and rr are `tool` dependencies, run through `go tool`. barm and rr are pinned
to pushed commits. Both clients come from `cmd/clientgen`, run
right after rr: it reads the routes through rr's `gen` library and the types
through ggen's, so the clients are regenerated with the router and a stale one
fails its `cmd/clientgen` test. The TypeScript one is checked with `pnpm check`
and `pnpm test` in `client/ts`.

## Filters

A list takes its filter as the body of a `QUERY` request. A filter with ids,
substrings, a time range, ordering and paging in it has more shape than a query
string carries well, and QUERY is the method that reads a body while promising,
like GET, to change nothing.

```sh
curl -X QUERY localhost:8080/api/users -H "Authorization: Bearer $TOKEN" -d '{
  "name_like": "hill",
  "email_like": "@acme.io",
  "created_after": "2026-01-01T00:00:00Z",
  "sort": "name", "desc": true,
  "page": {"limit": 20, "offset": 40}
}'
```

Every field is optional and the ones set all have to match. The text fields
match anywhere and ignore case, and `%` or `_` in them match themselves rather
than acting as wildcards. `sort` is checked against the columns that exist, so
nothing from a filter ever reaches the query text: values bind as arguments and
a sort column is looked up.

Every list is paged. A `GET` list, and a filter that asks for no page, return
`domain.DefaultLimit` rows, and `limit` is capped at `domain.MaxLimit`.

## Imports

`POST /api/posts/import` takes a JSON array of posts and writes them all in
one round trip. The array is decoded an element at a time while the inserts
are queued in a batch, which goes out when the array ends. A post that breaks
a rule, or names an author that does not exist, does not stop the others: it
comes back in `failed` with its place in the array, the post as it decoded
and every reason it was turned away. A body that is not a JSON array writes
nothing and answers 400. One import takes at most `domain.MaxImport` posts.

```sh
curl localhost:8080/api/posts/import -H "Authorization: Bearer $TOKEN" -d '[
  {"author_id": "AZm2Hn0Ld2iD7cO6wCuW3g", "title": "first"},
  {"author_id": "AZm2Hn0Ld2iD7cO6wCuW3g", "title": ""}
]'
```

`POST /api/posts/import/unbatched` answers the same, but reads the whole array
before it writes, and writes a post per round trip. It is there to compare
against.
